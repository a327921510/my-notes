# /a11y-audit — 可访问性体检

按 `accessibility.rule.mdc` 九个维度对一段 JSX / 一个文件 / 一个目录做完整 a11y 体检。

## 何时使用

- 接入 antd 之外的第三方组件后（容易丢 a11y）
- 大改样式后（容易破对比度、`outline:none` 等）
- 重要交互模块上线前（弹窗、表单、列表操作）
- 想在 PR 里附一份"a11y 已自检"证据

## 输入

```
/a11y-audit <file path | directory>

可选附加：
  --severity-only critical    只列 🔴 严重违例（默认全部级别）
  --component-list            生成"按组件分组"的报告而非按维度
```

## 工作流

按 `accessibility.rule.mdc` 的九个维度逐项扫描，每条违例标注严重等级：

| 等级 | 含义 | 影响 |
|---|---|---|
| 🔴 严重 | 键盘 / 屏幕阅读器**完全无法**完成核心操作 | 必须修 |
| 🟡 中等 | 可用但体验明显劣化 | 应该修 |
| 🟢 轻度 | 边缘场景 | 视情况 |

## 输出格式（严格）

```markdown
## A11y Audit: <被审目标>

### 总览
- 扫描文件数：X
- 发现违例：🔴 N1 / 🟡 N2 / 🟢 N3
- 严重程度判定：<可上线 / 建议修复后上线 / 必须修复>

### 🔴 严重违例（必须修）
1. **<违例类别>**（违反 accessibility.rule 第 X 节）
   - 文件：`path/to/file.tsx:123`
   - 当前代码：
   ```tsx
   <div onClick={handleSubmit}>提交</div>
   ```
   - 问题：键盘用户无法 Tab 聚焦、无法 Enter 触发；屏幕阅读器不会念"按钮"
   - 修复：
   ```tsx
   <button type="button" onClick={handleSubmit}>提交</button>
   ```

### 🟡 中等违例（应该修）
（同上格式）

### 🟢 轻度违例（视情况）
（一句话描述即可，不一定附代码）

### ✅ 已正确处理
- antd Form 自动提供了 label / aria-required / aria-describedby
- Modal 焦点 trap 正常工作
- (列出 2–4 条做对的，让作者知道 baseline 已经达标)

### 🔍 无法静态判断、需手测的项
- 色彩对比度：当前主题 token 的 #RRGGBB 与背景对比 = X，建议用 DevTools Contrast Ratio 工具复核
- 屏幕阅读器播报顺序：建议在 Mac VoiceOver / Windows NVDA 实际过一遍
- 键盘焦点视觉反馈：自定义按下态时 outline 是否仍可见

### 维度覆盖率
| 维度 | 检查通过 | 发现问题 |
|---|---|---|
| 1. 语义化 | ... | ... |
| 2. 键盘 | ... | ... |
| 3. ARIA | ... | ... |
| 4. 焦点管理 | ... | ... |
| 5. 色彩对比 | ... | ⚠️ 需手测 |
| 6. 异步状态 | ... | ... |
| 7. 表单 | ... | ... |
| 8. 图片媒体 | ... | ... |
| 9. antd 组件特例 | ... | ... |
```

## 行为约束

- **必须按九个维度都检查**——即使某维度无问题也要在覆盖率表中标注，证明"扫过了"，而不是"漏了"
- **必须区分"代码可判定"和"需手测"**：色彩对比度、实际 VO/NVDA 播报、键盘视觉焦点等场景，AI 给不了最终结论，必须明确告知用户去手测
- **不要把"建议"伪装成"违例"**：accessibility.rule 没明说的良好实践放到底部"建议"里，不要混进违例列表
- **antd 组件不要重复挑刺**：antd 已正确实现的 a11y（Modal 焦点 trap、Form label、Button keyboard 等）不应作为违例列出
- **修复代码必须可直接 copy-paste 用**：不要给伪代码 / 占位符
